# Инструкции для Codex GPT

Эти правила применяются ко всем файлам внутри папки `Codex GPT`.

## Обязательный старт каждого нового чата

1. Определи корень Git-репозитория и текущую ветку.
2. Проверь `git status --short --branch`.
3. Если рабочее дерево чистое, получи свежие данные из `origin/main` и обнови локальную ветку безопасным fast-forward или rebase. Если есть локальные изменения, не скрывай и не удаляй их: сначала классифицируй изменения и сообщи о расхождении.
4. Полностью прочитай `PROJECT_CONTEXT.md`.
5. Найди указанную там текущую каноническую версию рабочего скрипта и проверь, что она существует.
6. Кратко сообщи пользователю, какая версия и какой следующий шаг восстановлены.

Нельзя начинать доработку от случайной локальной копии или более старой версии, если в `origin/main` есть более свежая.

### Короткая команда запуска

Если пользователь пишет **«Прочитай сервер»** в любом регистре и с любыми знаками препинания, выполни обязательный старт из этого раздела: безопасно синхронизируй чистую ветку с `origin/main`, прочитай правила и `PROJECT_CONTEXT.md`, проверь текущий рабочий файл и сообщи восстановленное состояние.

Эта фраза разрешает только чтение и безопасное получение изменений с GitHub. Она не разрешает изменение скриптов, коммит или публикацию. При наличии локальных изменений ничего не перезаписывай и сначала сообщи пользователю.

## Общая память двух компьютеров и разных чатов

`PROJECT_CONTEXT.md` — общая память проекта. История чатов сама по себе между компьютерами не синхронизируется, поэтому после каждой значимой работы обновляй этот файл.

В обновлении обязательно фиксируй:

- дату;
- канонический рабочий файл и его версию;
- что изменено;
- как проверено;
- известные ограничения или ошибки;
- точный следующий шаг;
- важные решения пользователя, которые должны знать последующие чаты.

Не копируй в контекст огромный сырой лог чата или вывод инструментов. Сохраняй только проверенные факты и решения, достаточные для продолжения работы.

Если пользователь разрешил подготовку изменений к GitHub, рабочий файл и обновление `PROJECT_CONTEXT.md` должны попадать в один логический коммит, когда это возможно.

## GitHub и публикация

- Общие правила GitHub и запрет автоматической публикации заданы в корневом `../AGENTS.md` и обязательны для этой папки.
- Репозиторий: `vilsonv050/lotto-calc`.
- Общая ветка: `main`.
- GitHub — единственное общее хранилище проекта между компьютерами.
- Для проверки состояния используй `powershell -ExecutionPolicy Bypass -File .\SYNC_GITHUB.ps1 status`.
- Перед работой используй `powershell -ExecutionPolicy Bypass -File .\SYNC_GITHUB.ps1 pull`.
- После локальных изменений перечисли изменённые файлы и результаты проверок, затем обязательно спроси пользователя: «Заливать на GitHub?»
- Молчание, отсутствие ответа или переход пользователя к другой теме означает «не заливать».
- Не выполняй `git add`, `git commit`, `SYNC_GITHUB.ps1 push`, `git push`, не создавай pull request, релиз или тег без отдельной явной команды пользователя.
- Только после явного разрешения пользователя создай проверенный коммит и используй `powershell -ExecutionPolicy Bypass -File .\SYNC_GITHUB.ps1 push`.
- Не использовать OneDrive, Dropbox или ручное копирование как второй механизм синхронизации рабочей Git-папки.
- Перед началом работы: получить свежий `main`.
- После завершённого и проверенного изменения: обновить контекст и оставить изменения локальными до решения пользователя о публикации.
- Не использовать `git push --force`, `git reset --hard`, `git clean -fd` или массовое удаление неизвестных файлов.
- Не переписывать опубликованную историю без явного запроса пользователя.
- При конфликте между компьютерами не выбирать одну сторону вслепую: сохранить обе версии, сравнить их и разрешить конфликт осознанно.
- Ветка `github--привязка-4d989` устарела и относится к другому файлу. Не использовать её как основу для работы в `Codex GPT`.

### Дневная заливка на сервер

- Под «сервером» понимается `vilsonv050/lotto-calc`, ветка `main`.
- При срабатывании автоматизации «Сервер Git Hub» собрать опубликованные и локально завершённые результаты с момента последней записи, проверить их и подготовить новую запись в `PROJECT_CONTEXT.md`.
- Публиковать дневной комплект можно после явной команды пользователя в текущей задаче. Ответ «делай» является разрешением, если он дан непосредственно на предложение обновить сервер.
- В один дневной комплект включать только проверенные рабочие файлы, их необходимые производные сборки и `PROJECT_CONTEXT.md`. Не отправлять временные отчёты, кэши, секреты и посторонние локальные изменения.
- Перед коммитом выполнить `git fetch origin main`, проверить расхождение веток, полный diff, синтаксис и доступные тесты. После коммита использовать `SYNC_GITHUB.ps1 push` и подтвердить синхронизацию `main` с `origin/main`.
- Формат дневной записи: дата; файлы и версии; что изменено; как проверено; ограничения; решения пользователя; следующий шаг; SHA коммита после публикации, если он уже известен.
- Если рабочие файлы уже были опубликованы отдельными коммитами, дневная запись должна перечислить эти коммиты и не должна повторно менять файлы только ради отчёта.

## Режим изменения и правила версий скрипта

Перед изменением существующего скрипта получи однозначный выбор пользователя:

1. **Заменить текущий скрипт** — изменить указанный пользователем текущий файл без создания новой версии.
2. **Создать новую версию** — сохранить текущий файл без изменений и создать следующую свободную версию.

Если пользователь не выбрал режим, сначала спроси его и не решай самостоятельно. Не выполняй оба режима одновременно без прямой команды. Выбор режима не разрешает публикацию: после локальной проверки всё равно отдельно спроси, заливать ли изменения на GitHub.

- Уже созданные датированные версии не перезаписывать. Исключение возможно только для явно указанного пользователем текущего рабочего файла в режиме «Заменить текущий скрипт».
- Первая версия за день: `Статистика Тиражей_ДД-ММ-ГГ.txt`.
- Следующие версии того же дня: `Статистика Тиражей_ДД-ММ-ГГ_V1.txt`, затем `_V2`, `_V3` и далее.
- Перед созданием новой версии проверить содержимое папки и выбрать следующий свободный суффикс.
- Внутренний номер/заголовок скрипта и имя файла должны однозначно соответствовать новой версии.

## Проверка изменений

Для каждого изменения скрипта:

1. Проверь синтаксис JavaScript/bookmarklet.
2. Проверь затронутую логику на конкретном известном тираже или фактическом ответе API.
3. Если изменение касается универсальной логики, проверь несколько типов лотерей, а не только один пример.
4. Не считай визуально правдоподобный результат доказательством правильности финансового расчёта.
5. Не сохраняй ошибочный, неполный или прочеркнутый ответ API как корректный кэш.
6. В итоговом сообщении перечисли файл, проверки и оставшиеся ограничения.

## Безопасность данных

Не сохраняй в GitHub:

- пароли и токены;
- cookies и session storage;
- персональные данные;
- локальные профили браузера;
- временные файлы и кэши;
- секреты из переменных окружения.

Если такие данные обнаружены, не показывай их содержимое и не добавляй их в Git.
