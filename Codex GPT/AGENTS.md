# Инструкции для Codex GPT

Эти правила применяются ко всем файлам внутри папки `Codex GPT`.

## Обязательный старт каждого нового чата

1. Определи корень Git-репозитория и текущую ветку.
2. Проверь `git status --short --branch`.
3. Если рабочее дерево чистое, получи свежие данные из `origin/main` и обнови локальную ветку безопасным fast-forward или rebase. Если есть локальные изменения, не скрывай и не удаляй их: сначала классифицируй изменения и сообщи о расхождении.
4. Полностью прочитай `PROJECT_CONTEXT.md`.
5. Найди указанную там текущую каноническую версию рабочего скрипта и проверь, что она существует.
6. Кратко сообщи пользователю, какая версия и какой следующий шаг восстановлены.

Нельзя начинать доработку от случайной локальной копии или более старой версии, если в `origin/main` есть более свежая.

## Общая память двух компьютеров и разных чатов

`PROJECT_CONTEXT.md` — общая память проекта. История чатов сама по себе между компьютерами не синхронизируется, поэтому после каждой значимой работы обновляй этот файл.

В обновлении обязательно фиксируй:

- дату;
- канонический рабочий файл и его версию;
- что изменено;
- как проверено;
- известные ограничения или ошибки;
- точный следующий шаг;
- важные решения пользователя, которые должны знать последующие чаты.

Не копируй в контекст огромный сырой лог чата или вывод инструментов. Сохраняй только проверенные факты и решения, достаточные для продолжения работы.

Рабочий файл и обновление `PROJECT_CONTEXT.md` должны попадать в один логический коммит, когда это возможно.

## GitHub как источник истины

- Репозиторий: `vilsonv050/lotto-calc`.
- Общая ветка: `main`.
- GitHub — единственное общее хранилище проекта между компьютерами.
- Не использовать OneDrive, Dropbox или ручное копирование как второй механизм синхронизации рабочей Git-папки.
- Перед началом работы: получить свежий `main`.
- После завершённого и проверенного изменения: обновить контекст, создать понятный коммит и отправить его в GitHub.
- Не использовать `git push --force`, `git reset --hard`, `git clean -fd` или массовое удаление неизвестных файлов.
- Не переписывать опубликованную историю без явного запроса пользователя.
- При конфликте между компьютерами не выбирать одну сторону вслепую: сохранить обе версии, сравнить их и разрешить конфликт осознанно.
- Ветка `github--привязка-4d989` устарела и относится к другому файлу. Не использовать её как основу для работы в `Codex GPT`.

## Правила версий скрипта

- Не перезаписывать исходник и уже созданные датированные версии.
- Первая версия за день: `Статистика Тиражей_ДД-ММ-ГГ.txt`.
- Следующие версии того же дня: `Статистика Тиражей_ДД-ММ-ГГ_V1.txt`, затем `_V2`, `_V3` и далее.
- Перед созданием новой версии проверить содержимое папки и выбрать следующий свободный суффикс.
- Внутренний номер/заголовок скрипта и имя файла должны однозначно соответствовать новой версии.

## Проверка изменений

Для каждого изменения скрипта:

1. Проверь синтаксис JavaScript/bookmarklet.
2. Проверь затронутую логику на конкретном известном тираже или фактическом ответе API.
3. Если изменение касается универсальной логики, проверь несколько типов лотерей, а не только один пример.
4. Не считай визуально правдоподобный результат доказательством правильности финансового расчёта.
5. Не сохраняй ошибочный, неполный или прочеркнутый ответ API как корректный кэш.
6. В итоговом сообщении перечисли файл, проверки и оставшиеся ограничения.

## Безопасность данных

Не сохраняй в GitHub:

- пароли и токены;
- cookies и session storage;
- персональные данные;
- локальные профили браузера;
- временные файлы и кэши;
- секреты из переменных окружения.

Если такие данные обнаружены, не показывай их содержимое и не добавляй их в Git.
