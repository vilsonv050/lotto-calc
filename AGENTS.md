# Общие инструкции репозитория lotto-calc

Эти правила применяются ко всему репозиторию. Вложенные `AGENTS.md` могут добавлять специальные правила для своих папок, но не могут отменять запрет публикации без разрешения пользователя.

## Запрет автоматической публикации

- Любые изменения сначала выполняются и проверяются локально.
- Не выполнять `git push`, не создавать и не обновлять pull request, релиз или тег и не изменять GitHub иным способом без отдельной явной команды пользователя в текущей задаче.
- Команды «сделай», «исправь» и «обнови» разрешают локальные изменения, но не являются разрешением на публикацию.
- После завершения локальных изменений перечислить изменённые файлы, сообщить результат проверки и обязательно спросить: «Заливать на GitHub?»
- Пока пользователь явно не ответил «да», «залей», «отправь на GitHub» или равнозначной командой, оставить изменения локальными.
- Молчание, отсутствие ответа или переход пользователя к другой теме означает «не заливать».
- Не выполнять автоматически `git add` и `git commit`. Они допустимы после разрешения на публикацию либо по отдельной команде пользователя сделать локальный коммит без отправки.
- `git status`, `git diff`, `git log`, `git fetch`, `git pull` и чтение данных GitHub не считаются публикацией и разрешены, когда нужны для безопасной работы.

## Порядок работы

- Репозиторий: `vilsonv050/lotto-calc`.
- Основная ветка: `main`.
- Перед редактированием проверить корень репозитория, текущую ветку и `git status --short --branch`.
- Не скрывать, не удалять и не включать в свою работу посторонние изменения пользователя.
- Если рабочее дерево чистое, перед работой получить актуальный `origin/main`.
- После редактирования выполнить подходящие проверки и показать пользователю локальный результат.
- Только после отдельного разрешения на публикацию ещё раз проверить состав изменений, добавить относящиеся к задаче файлы, создать понятный коммит и отправить его на GitHub.
- После отправки проверить, что локальная ветка синхронизирована с `origin/main`.

## Правила заливки на сервер GitHub

- Под словами «сервер» и «сервер GitHub» в этом проекте понимается репозиторий `vilsonv050/lotto-calc`, ветка `main`.
- Фразы «залей на сервер», «обнови сервер», «залей на GitHub», «отправь на GitHub» и равнозначные им являются явным разрешением на публикацию только в текущей задаче и только для уже показанного пользователю состава изменений. Одиночное «делай» считается разрешением на публикацию лишь как прямой ответ на предложение обновить сервер в этой же задаче.
- Сигнал автоматизации «Сервер Git Hub» запускает проверку итогов работы и подготовку дневного отчёта. Сам по себе сигнал не отменяет проверок и не разрешает публиковать секреты, непроверенный код, конфликтующие или посторонние изменения.
- Перед заливкой обязательно:
  1. проверить ветку и `git status --short --branch`;
  2. выполнить `git fetch origin main` и убедиться, что локальный `main` не отстаёт от `origin/main`;
  3. просмотреть полный `git diff` и включить только относящиеся к работе файлы;
  4. выполнить подходящие синтаксические, автоматические и прикладные проверки;
  5. проверить добавляемые файлы на пароли, токены, cookies, персональные данные, локальные кэши и другие секреты;
  6. обновить `Codex GPT/PROJECT_CONTEXT.md` дневной записью.
- Дневная запись должна содержать дату, изменённые файлы и версии, выполненную работу, результаты проверок, известные ограничения, решения пользователя и точный следующий шаг.
- Проверенные рабочие файлы и соответствующее обновление `PROJECT_CONTEXT.md` по возможности отправлять одним логическим коммитом с понятным русским сообщением.
- Не включать в коммит неизвестные или не относящиеся к задаче изменения. При смешанном рабочем дереве сначала отделить и перечислить точный состав публикации.
- Публикация выполняется обычным push в `origin/main` через `Codex GPT/SYNC_GITHUB.ps1 push` или эквивалентный безопасный `git push origin main`. Pull request создаётся только по отдельной просьбе пользователя.
- Если проверки не прошли, обнаружен конфликт или локальный `main` отстаёт от сервера, публикацию остановить, ничего не перезаписывать и сообщить причину.
- Запрещены `push --force`, переписывание опубликованной истории и обход защиты ветки.
- После заливки проверить SHA нового коммита, повторно выполнить `git status --short --branch` и убедиться, что `main` совпадает с `origin/main`. В ответе перечислить опубликованные файлы, коммит и результаты проверок.

## Короткая команда «Прочитай сервер»

Фраза пользователя **«Прочитай сервер»** в любом регистре, с любыми знаками препинания или дополнительными пробелами означает:

1. Проверить локальный репозиторий, ветку и незавершённые изменения.
2. Если рабочее дерево чистое, безопасно получить свежую ветку `origin/main`.
3. Прочитать этот `AGENTS.md`, относящиеся к рабочей папке вложенные `AGENTS.md` и `Codex GPT/PROJECT_CONTEXT.md`.
4. Проверить указанный в памяти текущий рабочий файл.
5. Кратко сообщить пользователю восстановленную версию, состояние синхронизации и следующий шаг.

- Эта команда разрешает только чтение, `git status`, `git fetch` и безопасный `git pull`.
- Она не разрешает изменение скрипта, `git add`, `git commit`, `git push` или любую публикацию на GitHub.
- Если есть локальные изменения или конфликт, ничего не удалять и не перезаписывать; остановить синхронизацию и сообщить пользователю.

## Режим изменения скриптов

Перед изменением существующего скрипта должен быть выбран один режим:

1. **Заменить текущий скрипт** — изменить указанный пользователем текущий файл без создания новой версии. Разрешено только по явному выбору пользователя.
2. **Создать новую версию** — оставить текущий файл без изменений и создать следующий свободный номер версии по правилам соответствующей папки.

- Если режим не указан однозначно, спросить пользователя до изменения или сохранения скрипта.
- Не заменять текущий скрипт и не создавать новую версию одновременно без прямой команды пользователя.
- Режим изменения не даёт разрешения на публикацию. После локальной работы всё равно отдельно спросить, заливать ли изменения на GitHub.
- При публикации отправлять только выбранный пользователем вариант и необходимые сопутствующие файлы.

## Безопасность Git и данных

- Не использовать `git push --force`, `git reset --hard`, `git clean -fd` и другие операции, способные уничтожить опубликованную историю или локальные данные.
- При конфликте между компьютерами сохранить обе версии, сравнить их и разрешить конфликт осознанно.
- Не сохранять в Git пароли, токены, ключи, cookies, session storage, персональные данные, локальные профили браузера, кэши и другие секреты.
